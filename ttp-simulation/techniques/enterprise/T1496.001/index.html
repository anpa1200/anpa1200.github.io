Complete technique description

Adversaries may leverage the compute resources of co-opted systems to complete resource-intensive tasks, which may impact system and/or hosted service availability.

One common purpose for Compute Hijacking is to validate transactions of cryptocurrency networks and earn virtual currency. Adversaries may consume enough system resources to negatively impact and/or cause affected machines to become unresponsive.[Kaspersky Lazarus Under The Hood Blog 2017] Servers and cloud-based systems are common targets because of the high potential for available resources, but user endpoint systems may also be compromised and used for Compute Hijacking and cryptocurrency mining.[CloudSploit - Unused AWS Regions] Containerized environments may also be targeted due to the ease of deployment via exposed APIs and the potential for scaling mining activities by deploying or compromising multiple containers within an environment or cluster.[Unit 42 Hildegard Malware][Trend Micro Exposed Docker APIs]

Additionally, some cryptocurrency mining malware identify then kill off processes for competing malware to ensure it’s not competing for resources.[Trend Micro War of Crypto Miners]

Container Creation · source-mapped

DC0072 collection page — Collect runtime create events and image/container IDs; correlate with API audit to establish the initiating identity.

Providers and collection configuration

  • Docker Engine events: Daemon lifecycle events for containers and images; collect continuously.
  • Kubernetes API audit: Control-plane context in Kubernetes, not a replacement for runtime observations.
  • Subscribe to the lab daemon event stream with filters for the relevant object/action; send it to a durable collector.
  • Record runtime/container ID, image digest, action, timestamp and host. Join orchestrator identities where available.
  • Use a protected collector connection. Docker socket access is privileged; never expose it publicly or grant it to the website.

Required normalized fields: container_id, image_digest, action.

Host Status · source-mapped

DC0018 collection page — Collect agent heartbeat and OS health independently; record missed polls, last-seen time and monitor health.

Providers and collection configuration

  • osquery: Scheduled host-state queries; supported tables and privileges vary by OS. Select a table that actually exposes the required object.
  • Linux Audit plus inventory snapshots: Events explain changes; snapshots describe state at collection time.
  • Define the inventory query, allowed host set, interval and least-privileged reader. Store a stable asset ID, observation time and collector version.
  • Keep successive snapshots and calculate additions, removals and changed attributes. Pair state changes with audit events when available.
  • Export collector health and missed-poll counts so a missing snapshot is not misclassified as a missing asset.

Required normalized fields: asset_id, status, heartbeat_age_seconds, collector_healthy.

Network Connection Creation · source-mapped

DC0082 collection page — Enable scoped Sysmon NetworkConnect (3), disabled by default, or a platform-equivalent process-aware network sensor.

Providers and collection configuration

  • Microsoft Sysmon: Windows event-based collection; enable the event types needed below.
  • Linux Audit: Linux alternative for supported system-call and file events; different semantics and fields.
  • Apple Endpoint Security clients: macOS alternative where the subscribed event exists; requires an entitled, approved client, not an iOS collector.
  • On a disposable Windows host, review the installed Sysmon schema and current configuration; merge scoped event filters into the existing policy rather than replacing it.
  • Forward Microsoft-Windows-Sysmon/Operational to the lab collector. Preserve event ID, timestamp, computer, process identifiers and the original event.
  • For Linux or macOS, select the equivalent sensor separately and test its emitted fields; a Windows event ID does not transfer across platforms.

Required normalized fields: process_guid, destination_ip, destination_port, protocol, initiated.

Network Traffic Content · source-mapped

DC0085 collection page — Scope approved packet capture/protocol content collection to the lab flow; retain capture provenance and truncation indicators.

Providers and collection configuration

  • Monitor capture loss, truncation and exporter sampling. Capture payload only with approval and restrictive retention; encryption normally prevents plaintext inspection.

Scheduled Job Creation · source-mapped

DC0001 collection page — Enable Audit Other Object Access Events for Windows task creation (4698); retain task XML. For cron/systemd timers, collect scheduler definitions and change events separately.

Providers and collection configuration

  • Windows Security auditing: Policy-dependent account, object, task and logon records on the host that performs the operation.
  • Use a lab-only GPO under Computer Configuration → Windows Settings → Security Settings → Advanced Audit Policy Configuration. Enable the specific subcategory named below.
  • For object-level auditing, configure a narrow system access control list (SACL) on the test object in addition to policy. Do not audit an entire production directory by default.
  • Forward Security events from the responsible host or controller; retain subject and target identities, object identifiers, result and original XML. Confirm effective policy with auditpol /get /category:*.

Required normalized fields: task_name, action, principal, schedule, program.

DET0540 Multi-Platform Behavioral Detection for Compute Hijacking

MITRE detection strategy

AN1489 Analytic 1489

Sustained execution of resource-intensive processes (e.g., cryptocurrency miners), often launched via scheduled tasks, WMI, or PowerShell. These processes frequently establish persistent external connections and attempt to evade detection using masqueraded or renamed binaries.

Platforms: Windows.

  • Process Creation — WinEventLog:Sysmon; channel EventCode=1.
  • Network Connection Creation — WinEventLog:Sysmon; channel EventCode=3, 22.
  • Scheduled Job Creation — WinEventLog:Security; channel EventCode=4698.

AN1490 Analytic 1490

Unusual long-running processes consuming high CPU cycles (e.g., via 'top' or 'ps') initiated via cron, shell scripts, or Docker. Connections to known mining pools or DNS over HTTPS usage as evasion.

Platforms: Linux.

  • Process Creation — auditd:SYSCALL; channel execve.
  • Network Traffic Flow — NSM:Flow; channel Outbound connection to mining pool port (3333, 4444, 5555).
  • Scheduled Job Creation — linux:cron; channel Scheduled execution of unknown or unusual script/binary.

AN1491 Analytic 1491

Persistent or background daemons (e.g., plist or launchd jobs) spawning high-CPU processes like xmrig or cpuminer. Outbound encrypted traffic to IPs/domains commonly used by mining proxies.

Platforms: macOS.

  • Process Creation — macos:unifiedlog; channel launchd or cron spawning mining binaries.
  • Network Traffic Content — macos:unifiedlog; channel Persistent outbound connections with consistent periodicity.

AN1492 Analytic 1492

Ephemeral or unauthorized container instantiation using public images (e.g., from DockerHub) that initiate high CPU usage shortly after startup. Often scheduled via Kubernetes or Docker socket abuse.

Platforms: Containers.

  • Container Creation — containerd:events; channel create.
  • Process Creation — auditd:SYSCALL; channel execve.
  • Network Traffic Flow — NSM:Flow; channel Outbound traffic to mining pool upon container launch.

AN1493 Analytic 1493

Unauthorized instance creation in unmonitored or unused regions. Burst of compute-intensive jobs in spot instances or sudden spike in resource usage in legitimate VMs.

Platforms: IaaS.

  • Instance Start — AWS:CloudTrail; channel RunInstances.
  • Host Status — AWS:CloudWatch; channel Unusual CPU burst or metric anomalies.

Anomaly engineering worksheet

Start from the exact analytic above. The collection-specific lenses below are analyst recommendations; they do not assert that an arbitrary statistical deviation detects this technique.

  • Container runtime: Per workload image and namespace: rare process starts, unexpected image/privilege changes and new network relationships. Use workload/deployment identity, not short-lived container IDs alone.
  • Host state and inventory: Compare authorized state snapshots: first-seen drivers/services/modules, unexpected configuration drift and integrity changes. Record collection cadence; absence in a sample is not evidence of deletion.
  • Cloud control plane: Per account, role, region and API: rare actions, new role-resource relationships, enumeration bursts and configuration changes. Separate deployment automation and organization-level administrative activity.
  • Endpoint activity: Per host role and user: rare process/object combinations, bursts of object access or modification, and ordered parent/action sequences. Compare maintenance windows and signed software rollout activity.
  • Network and protocol telemetry: Per source and observation point: connection rate, destination-host/port fan-out, response/failure ratio and previously unseen destinations. Compare equivalent time windows; separate authorized scanners, NAT and sampling effects.
  • Windows and directory audit: Per principal, host and object: unusual access/request rates, new principal-object relationships, and changes outside approved administration windows. Control for service accounts and scheduled directory maintenance.
  1. Define an entity/peer group and feature; exclude the evaluation period from baseline training.
  2. Use representative normal and maintenance activity. Do not invent a production threshold from a synthetic example.
  3. Evaluate held-out behavior-positive and benign cases; measure false positives, misses and telemetry loss separately.
  4. Keep abnormality separate from maliciousness. Correlate with the behavior-specific source evidence.
